# Fresh prior-translation search, one batch

**Who reads the output.** A reader on `/book/<id>` sees one plain answer: "Earlier English translation", with the link, or "First English translation", with the date we searched and the searches run. Derek wants as many books as possible to carry one of the two (2026-10-28). Output first: write, then spot check. Do not gate on card review; that system is being archived (#7598).

**Cost.** About 27 s and 23K Sonnet tokens a book. On a Max 20x account that is about 64 books per 1% of the 5-hour window and about 380–760 books per weekly point, so roughly $0.001 a book of subscription ($0.057 at API price). It runs on subscriptions only, never the API.

## Steps

Work in a batch directory outside the repo, for example `~/ft-batches/<date>-<n>/` on the laptop or `/root/ft-batches/...` on a box. **Never a session scratchpad:** `/private/tmp` is cleared on reboot, and batch 3 sat there, searched and un-ingested, until someone looked (2026-10-28). Run commands from a checkout on `main`, with the env loaded (`set -a; source .env.production.local; set +a`).

1. **Pick the account.** `climits status`, then choose an account with week headroom and nothing else running on it. Confirm with `CLAUDE_CONFIG_DIR=<dir> claude auth status`, because a CLI's login is often not the account you think (memory: lesson_check_which_account_a_cli_uses). On the laptop, team@ is `~/.claude-team`.
2. **Select.** `node scripts/ft-search/select-batch.mjs --n 1000 --out <dir>`. It prints how many books are still eligible (visible, translated, not English, no fresh search yet) and draws in priority tiers: never searched by any method first, then books the old card system searched but left unbadged and uncredited, then badged or credited books last. Each prompt also carries up to 10 rows from Supabase `translation_catalogs` for the same author surname, ranked by title overlap, as leads to check (it prints how many prompts got leads). **One search per work:** when `scripts/ft-search/propagation-gate.json` says `enabled` (the gate passed, see Measured), it draws one representative per `work_id` and writes `<dir>/siblings.json` (rep → sibling volumes with the same title once the volume number is removed; collected-works sets, Tengyur/Kangyur, `kr:` juan sets and differing titles are never grouped and are searched themselves). The rep's prompt says it is one of N volumes and asks for the WHOLE work. `--one-per-work` / `--no-one-per-work` override the file.
3. **Search, detached.** `CLAUDE_CONFIG_DIR=<dir> nohup caffeinate -i scripts/ft-search/run-batch.sh <dir> 4 >/dev/null 2>&1 & disown`. On a box, run it under `claude-job.sh` instead. Start the guard beside it: `nohup scripts/ft-search/meter-guard.sh <dir> <email> 85 20 >/dev/null 2>&1 & disown` (stops the batch at 85% of the 5-hour window, 20% of the week, or when the meter cannot be read). It is resumable: after a usage limit or a guard stop, remove `STOP` and run it again. Watch `<dir>/progress.log`; it ends with BATCHDONE. Never poll from a big session (memory: feedback_token_efficiency_fork_protocol). **The batch then applies itself** (`run-batch.sh`; nothing waits on the launching session): parse → `ingest.mjs --apply` (siblings of a `none_found` rep get the same badge, each with its own attempt row "inherited from <rep attempt>"; siblings of a credit, partial or unclear rep get nothing and stay eligible) → catalogue harvest `--since` the ingest start → `update-homepage-stats.mjs` → credit recheck (`prepare`, search in a clean env, `apply --no-retract`) → ONE ntfy page with counts and the number of retractions held (`<dir>-recheck/retractions-held.json`). Retractions stay manual. A failing step pages and stops the chain. Launch it with the env loaded (MONGODB_URI, SUPABASE_*): without it the page says nothing was applied. `NO_AUTO_APPLY=1` keeps the old behaviour (parse + dry run + page). For an unattended run use `scripts/ft-search/nightly.sh <config-dir> <email> <n>` (selects, starts the guard and the batch, records the dir in `~/ft-batches/last-nightly.txt`).
4. **Parse and check links** (automatic since 2026-10-29; by hand only with `NO_AUTO_APPLY=1` or after a failed step). `python3 -I scripts/ft-search/parse-results.py <dir>` prints the verdict counts and how many links load.
5. **Ingest** (automatic: `--apply`). `node scripts/ft-search/ingest.mjs <dir>` (dry run), read the tallies, then add `--apply`. Report the counts: `prior_credit`, `first_new_badge`, `prior_conflicts_badge_held`, `prior_link_rejected`.
5b. **Add the credits to the catalogue.** `node scripts/enrichment/harvest-ft-into-translation-catalogs.mjs --from-credits` (dry run), then `--apply`. It copies every linked `books.prior_translation` since `--since` (default 2026-10-27) into `translation_catalogs` as `sl_prior_credit_linked`, deduped on write, so the next batch's prompts carry it as a lead. It takes several minutes (one SELECT per row): run it in the background.
6. **Show.** Run `node scripts/maintenance/update-homepage-stats.mjs` (env loaded). The homepage count is read from the cached `system_config.homepage_stats`, which a release does not recompute; after batch 2 it still said 4,557 until this ran (5,362). Then, if a release is more than an hour away, run `scripts/ft-search/revalidate.sh <dir>`. Then open two changed books (one credit, one new first) and grep the HTML for "Earlier English translation" / "First English translation". A row count is not a render check.
7. **Old-found conflicts.** List the new first badges whose book has an old `first_translation_attempts` row with `result: found` (any method other than `claude_subagent_verify`). Make one adjudication call each: is the old named prior a real English translation of THIS work? Where the new search wins and `translation_verification.disposition` is `translation_found`, set it to `confirmed_first`: the book-page timeline renders that field as "Earlier English translation", next to the new badge. Where the old search wins, remove the badge and credit the prior. Revalidate those pages. There is no script for this step yet; list the books with a Mongo query on `first_translation_attempts` and give one agent the whole list.
8. **Held conflicts, same run.** Do not leave a held book saying "No prior translation found" while our own search says otherwise. `node scripts/ft-search/held.mjs prompts <dir>/held`, run it with `run-batch.sh <dir>/held 3`, then `held.mjs apply <dir>/held` (dry run) and `--apply`. One call per book checks the claimed prior is real, the SAME text and complete (a translation of the ancient source does not defeat a book that is itself a translation or commentary). Complete → badge removed and prior credited; partial → badge kept and a partial credit added; anything else → badge kept and the attempt row marked `held_adjudication`, so it is not held again. `--since` defaults to 2026-10-27: older `claude_subagent_verify` rows came from the ft-verify card rounds, which already judged them.
9. **More than one prior.** Derek, 2026-10-28: post every real earlier translation, old and new. Where an old search named a different translation from the fresh credit (both named, year and translator differ), check it is real and the same text, and add it as a `translation_verification.validated_translations` pick with `disposition: translation_found`; the timeline lists every pick, oldest first. Do not add one on a badged book.
9b. **Recheck the credits, every batch.** A credit is a claim that the WHOLE book is already in English; the search over-claims. `node scripts/ft-search/recheck-credits.mjs prepare <dir>-recheck --since <batch start>`, run it with `run-batch.sh` (`prepare` writes `NO_POSTRUN`, so the runner does not ingest these answers), then `apply <dir>-recheck` (dry run) and `--apply --no-retract` (which also writes `retractions-held.json`; the batch does all of this itself now): partials become `scope: partial` at once. List the `not_a_translation` / `wrong_work` ones for Derek with links and the reason, retract on his word (`--apply` without `--no-retract`, or by id), and re-search those books: `select-batch.mjs --ids <file>` + `ingest.mjs --research`.
9c. **Record errors.** The search answers `metadata_issue` as `{kind, right_value}` (kind: none, author_is_printer, author_is_editor, author_is_uploader, author_is_root_text_author, date_is_upload_date, wrong_volume, wrong_language, other). `node scripts/ft-search/metadata-issues.mjs <dir>` (env loaded) prints counts by kind and writes `<dir>/metadata-issues.csv` for every kind but none/other (book url, current value, proposed value). It never writes to books: fix the clear ones through `setCatalogueFields()` with a `book_events` row; leave the rest.
10. **Spot check.** 10 random credits and 10 random new firsts. Give all 20 to ONE Opus agent (a judgement step; one agent per item would break the ~8-subagents-a-session cap): open each credited link; for each first, run 4-6 refutation searches and report how many it actually ran. Set any credit it calls partial to `scope: partial` with a `book_events` row, and revalidate. Post the counts and the error rate on #7598.
11. **Record.** Archive the batch directory to `sourcelibrary-ops/evals/ft-fresh-search/<date>-<n>/`, add a line to `~/sourcelibrary-ops/RUNNING.md`, and comment on #7598.

## Keep this skill current (required, every batch)

This skill learns only if the session that ran it writes the lesson down. Before you report a batch done:
- **Anything that broke, surprised you or cost a rerun** goes under *Traps* below, as one line with the date and the fix. Make the fix in the script, in the same PR. A trap that can become a check goes in the script, not just here.
- **Changed numbers** (books per weekly point, error rates from steps 8 and 10, the eligible count) go in *Measured* below, with the date.
- If the spot check shows more than about 15% missed priors among new firsts, stop scaling. Add a second, independent search for `none_found` before badging, and say so on #7598.
- Commit these edits in a PR (`tier:auto` handles docs and scripts).

## Unattended (box) run

**Installed 2026-10-29 on Hetzner main** (root crontab; backup in /root/crontab-backup-*.txt). It runs from its own detached worktree `/root/ft-code`, reset to origin/main before each run. Do not point it at `/root/sourcelibrary`, which carries untracked debris and has no branch. Two lines, one per account, each with its own config dir:
`30 1 * * * export PATH=/usr/local/bin:/usr/bin:/bin; cd /root/ft-code && git fetch -q origin main && git reset -q --hard origin/main && ENV_FILE=/root/sourcelibrary/.env.production.local FT_CAPW=70 FT_PARALLEL=6 sh scripts/ft-search/nightly.sh /root/.claude-team team@sourcelibrary.org 1500 >> /root/ft-batches/nightly.log 2>&1`, and the same at `30 13` with `/root/.claude-derek derek@sourcelibrary.org`. The PATH is load-bearing: cron's default PATH has no `claude` or `climits` (/usr/local/bin). FT_CAPW raises the guard's weekly cap from 20%, which would stop a run at once on an account already past it. A 20-book run (2026-10-29, `/root/ft-batches/2026-10-29-nightly-2129`) went through every step in under two minutes, about 10 s a search on the box. It checks `claude auth status` against the email, refuses to start while the last nightly batch is still running, excludes every un-ingested batch dir, and pages ntfy if it cannot start. Everything after BATCHDONE is `run-batch.sh`. The only human step left is the retractions page.

## Traps
- 2026-10-29 · Sibling volumes were searched one by one (2,201 of 11,439 unsearched books shared a `work_id` with another eligible book). Now one rep per work, behind the gate in `propagation-gate.json`; ingest refuses a `GATE` dir (the gate is read-only). Never extend grouping to collections: their volumes are different works.
- 2026-10-29 · `run-batch.sh` now applies the batch, so a recheck or held dir run through it must not: `recheck-credits.mjs prepare` and `held.mjs prompts` write `NO_POSTRUN` and the runner stops after the searches. A new dir type that is not a search batch needs the same marker, or its answers get ingested as a search.
- 2026-10-29 · `metadata_issue` is now `{kind, right_value}`; older results hold a free-text string (counted as `legacy_text`).
- 2026-10-29 · Several guards and the menubar app each polled the usage endpoint. `meter-guard.sh` now shares `~/.cache/ft-meter.json` (refreshed under a `mkdir` lock when 150 s old; a cache older than 10 min counts as blind).
- 2026-10-29 · `claude auth login --email X` does not choose the account: the grant goes to whoever the browser is signed in as (a derek@ login landed as team@). Have Derek sign in in a private window first, keep each account in its own `CLAUDE_CONFIG_DIR`, and check `claude auth status` before launching.
- 2026-10-29 · The prompt said "complete or substantial" and let a Wikipedia page or a study stand in, and ingest wrote `scope: complete` for every credit, even when the search's own note said "covers the odes only". Recheck of 1,018 credits: 323 partial, 9 not a translation or a different work. The prompt now defines a prior as a translation of ALL the book and asks for book_contains / translation_covers; step 9b rechecks anyway.
- 2026-10-29 · A `metadata_issue` field worded "empty, or what is wrong" fired on 735 of ~900 answers ("no clear error", approximate dates). It now says leave EMPTY unless clearly wrong, and lists what counts.
- 2026-10-29 · The usage endpoint 429s for 30+ minutes with three guards on two accounts; BLIND_MAX=30 (an hour) rode it out. No extra usage is enabled on any account, so a blind guard cannot overspend; it can only stop early.
- 2026-10-29 · Two guards on one account plus the menubar made the usage endpoint return 429, and the guard reads that as blind: batches 4 and 6 were one reading from a false stop. The guard now stops after `BLIND_MAX` (default 5, ten minutes) blank readings in a row.
- 2026-10-29 · Parallel batches: draw with `select-batch.mjs --exclude <other batch>/ids.txt`, or two un-ingested batches draw the same books. Ship a batch to a box as one `tar | ssh` stream; `scp -r` of 2,000 prompts crawled (387 files in five minutes).
- 2026-10-29 · Launching with the env loaded put `ANTHROPIC_API_KEY` in front of the subscription login: batch 4's first 18 calls went to the API and failed only because that key was invalid ($0). `search-one.sh` now runs `claude` in a clean env (`/usr/bin/env -i`, HOME/PATH/USER/LANG/CLAUDE_CONFIG_DIR only). Use the full path: uv installs an `env` script in `~/.local/bin` that shadows `/usr/bin/env` and runs nothing, silently (empty output, exit 0). Check the first `.json` for `Invalid API key` or a nonzero API cost before leaving a batch.
- 2026-10-29 · Batch 3 finished at 20:40Z and nobody ingested it: steps 4–11 waited on a session that never came back, in a scratchpad that a reboot would have wiped. `run-batch.sh` now runs the parse and dry run itself and pages ntfy; keep the batch dir in `~/ft-batches/`.
- 2026-10-29 · The fresh search never read `translation_catalogs`, and nothing wrote its credits back. Prompts now carry catalogue leads (step 2) and step 5b writes the credits back. Leads are unverified: compare batch 4's prior-found rate with batch 3's before trusting them.
- 2026-10-29 · `revalidate-book` returns 429 to a second caller while `revalidate.sh` runs. Retry single pages after it finishes.
- 2026-10-28 · The book page has two returns. The redesigned layout returns early, so a component mounted in the later return never renders (#7603 → #7608). Check the live HTML, not the diff.
- 2026-10-28 · A result file can hold two JSON lines when two runs wrote the same id. `parse-results.py` keeps the last line with a verdict; without that, about 5% were dropped.
- 2026-10-28 · A blank `climits json` reading is a one-off, not a broken login.
- 2026-10-28 · `revalidate-book` returns 429 above about 1 call a second; the script goes one at a time with backoff.
- 2026-10-28 · Searches that curled `/api/books/<id>` anonymously spent the laptop's anonymous budget and read the crawler notice instead of the record (5 of 174, batch 2). `select-batch.mjs` now fetches each record with `~/.sl-internal-key` and embeds it in the prompt; a missing key falls back to the curl and says so. Never put the key itself in a prompt.
- 2026-10-28 · **The account meter is not this job's cost.** Other work ran on team@ during batch 2 (14%→39% of the 5-hour window, 5%→9% of the week), so the meter cannot be attributed to the batch. Cost the batch by summing `total_cost_usd` over its own output JSONs, and read the meter only as headroom. The earlier "books per weekly point" figures (Measured below) carry the same contamination.
- 2026-10-28 · The old system's "found" verdicts are mostly wrong. In batch 2, 70% of books had an old search, and 71 of the 807 fresh badges contradicted an old "found". On adjudication the fresh search was right in 68: 42 old priors do not exist, and 14 are a different work. 9 of those pages showed both "First" and "Earlier English translation" (from `translation_verification`) until step 7 cleared them.
- 2026-10-28 · **A blind meter must stop the batch, not wave it through.** climits' own team@ token expired (`invalid_grant`) while the CLI login still worked, so the guard read nothing and would never have fired. `meter-guard.sh` now touches `STOP` and kills the runner after two blank readings in a row; re-login with `climits add team@sourcelibrary.org`.
- 2026-10-28 · The shared main checkout can lag `origin/main` by days (batch 3: `scripts/ft-search/` was missing there). Run from a fresh worktree, or `git archive origin/main scripts/ft-search | tar -x` into the batch's scratch dir.
- 2026-10-28 · Held conflicts were left as "No prior translation found" on the page while our own search had found one. Settle them in the same run (step 8); they are the most visible error the batch can leave.
- 2026-10-28 · Booksellers, Goodreads and Wikipedia are weak citations. Booksellers are rejected (`BAD_HOSTS` in `ingest.mjs`). Wikipedia is accepted for now (30 of 277 links); swapping in a better link is open.
