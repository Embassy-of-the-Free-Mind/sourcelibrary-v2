# A test that greps source is not a guard

**Read this when:** Writing a test that pins behaviour, or writing a fixture for one.

*Split out of `CLAUDE.md` on 2026-08-04. The text is unchanged apart from cross-references repointed to their new files. See `.claude/docs/knowledge-layer.md` for why this tier exists.*

---

A unit test whose every assertion is "this string appears in this file" can only catch **deletion**, never **wrongness**. `tests/unit/tenant-account-menu.test.ts` (#3383) asserted seven such facts — including one pinning the exact `pathname.startsWith('/embed/')` check that was the bug — and passed green the entire time the feature was broken in production. It was reverted along with the code it "guarded".

Source-shape assertions are legitimate for **absence** invariants, where deletion *is* the failure mode: `tests/unit/soft-404-loading-guard.test.ts` pins that certain `loading.tsx` files do not exist, and re-adding one genuinely reintroduces the soft-404. That test earns its keep; a shape test for *behaviour* does not.

For behaviour, the assertion has to exercise the thing: render the component under the condition (a simulated tenant host), call the function (`proxy()` directly, per the tenant section above), or hit a deployed URL and check the response. **Before writing a guard, ask what code change would make it fail — if the answer is only "deleting this line", it is documentation with a green checkmark, not a test.**

**Don't reason about that question — run it.** Delete the guarded line, watch the test go red, restore it. Two source-shape guards written in one session (#3484/#3488) both passed *with the code they guarded deleted*, and neither failure was visible by reading the test: one asserted `toContain('hasSearchTerm')` + `toContain('offset === 0')`, where both tokens occur elsewhere in the same file; the other asserted `/tenantId/` against a call body and was satisfied by the **explanatory comment sitting directly above `tenantId,`**. A source assertion matches the whole file, comments included — so scope it to a slice, strip comments before matching, or assert a composite string whose position relative to the call is checked. The negative control is the only thing that distinguishes a guard from a decoration.

**The mirror failure: a source guard can also be too STRICT, and it fails in the direction that looks responsible.** Everything above is about guards that are too weak — they pass when they should fail. The same technique breaks the other way when the assertion pins *how the code is spelled* rather than *what reaches what*. In #4159 a guard on `SiteHeader.tsx` required the literal `!isGlobalOnlyNavHref(child.href)`, to ensure dropdown children are filtered against the tenant global-only list. Wrapping the argument — `isGlobalOnlyNavHref(canonicalPath(child.href))`, needed because the nav now localizes hrefs and a Spanish header holds `/es/works` — turned it red, on a change that *strengthened the exact thing the guard exists for*.

A too-strict guard costs more than the noise: it reads as a real regression, so the honest response is to revert, and reverting means abandoning a correct fix to satisfy a decoration. **Assert the relationship, not the expression** — require `child.href` to appear *inside* the predicate call, not to be its entire argument. And when a guard fails on your change, ask which of the two it is before you touch anything: did you break the behaviour it protects, or only the spelling it happened to record? Editing a guard test is legitimate when its stated intent still holds and only the pinned syntax moved — say so in the commit, and never widen it so far that the negative control above stops going red.

**A parity test between two implementations does not test either one — and a parser of MODEL output needs a fixture copied from the prompt.** Everything above is about a single guard being weak, strict or fabricated. Two guards can also agree with each other and both be wrong: in #4456 five pipeline scripts held a `parseDetectedImages` that walked `<image>…</image>` sub-tags, a shape no OCR prompt in this repo has ever asked for — the prompt asks for a JSON array — so it returned `[]` on every page for as long as it existed. A parity test against a fork would have passed; there was no fork, and the previous consolidation (#4443) correctly declined to treat it as one. What no test asserted was the one thing that mattered: **feed the parser the prompt's own documented example and require a non-empty result.** The `if (parsed.length > 0)` guard at each of the five write sites then turned the empty result into silence — no error, no row, nothing to notice, across 31,210 pages holding the block. Whenever a function's contract is with a *prompt* rather than with other code, the fixture must be copied out of the prompt text (this is the rule above, with the prompt as "the real source"), and the assertion must be that it yields something — because the failure mode of a parser reading the wrong format is not a wrong value, it is a plausible empty one. Corollary for the write site: `if (x.length > 0)` is the shape that makes a dead parser invisible; if that guard exists, some test must prove the non-empty branch is reachable.

**A fixture you INVENTED is evidence about you, not about the system.** The rule above assumes the test's *input* is real and only its assertion is in doubt. A third guard failed the same way in #3584 with a real assertion and fabricated input: the control for a diacritic-folding fix hand-wrote a title page as `"… IKHWÁNU-S SAFÁ. Translated from the Hindustani."`, and "Translated" matched the title's own `translation` token through the matcher's six-character prefix rule (`transl`). It passed **with the fold deliberately removed** — a real code path, exercised, asserting nothing. The database's actual page holds only `# IKHWÁNU-S SAFÁ.` and no such phrase. Two details made it invisible: the stopword list screened `translated` but not `translation`, and the fixture was written *after* the wanted verdict was known, which is how invented evidence acquires exactly the properties it needs. **Capture fixture text from the real source before writing the assertion, never after** — a fixture drafted toward a known answer will reach that answer by whichever path is available, and you will not know which. This is the paired-artifact rule applied to test data: the fixture *claims* to stand for the real artifact, and nothing checks that it does.

**A guard can also be right about every case it looks at, and look at almost none of them.** The failures above are all about the *assertion*. This one is about the *scope*: which call sites the guard even examines. `scripts/audit/new-field-writes.mjs` exists to fail a PR that `$set`s an unknown `books` field. On 2026-08-31 a PR adding `pages_translatable` passed it, green, while doing exactly that (#4493). The guard attributes a `$set` to `books` by walking **900 characters** forward from a `collection('books')` call; `recount-page-stats.mjs` hoists `const books = db.collection('books')` to line 146 and writes at line 191. Outside the window, so never attributed, so never checked.

The window is not a mistake — it replaced a file-wide sweep that produced 814 false positives, and the comment above it is right that a lint which cries wolf is worse than no lint. The defect is that the surviving rule catches the **inline** form (`db.collection('books').updateOne(…, { $set: … })`) and misses the **hoisted** form, which is the dominant pattern in `scripts/`. Its coverage is therefore a function of *code style*, not of correctness, and a clean run means "no inline violations", not "no new fields". Nobody reading the green check can tell those apart.

**So a negative control has to vary the shape of the code, not just its content.** Deleting the guarded line proves the guard fires *somewhere*; it says nothing about where it is blind. Write the violation twice — once in the idiom the guard was built against, once in the other common idiom in the codebase — and confirm both go red. If you cannot state which call sites a guard does *not* examine, you do not know what its green means.
